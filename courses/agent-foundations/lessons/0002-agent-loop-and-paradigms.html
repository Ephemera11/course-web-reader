1. Agent 循环：ReAct 是怎么转的

Anthropic 文里说："Agents are typically just LLMs using tools based on environmental feedback in a loop." 拆开就是四步不断重复——这就是 ReAct（Reason → Act → Observe）：

①感知
读目标+历史
②推理
想下一步
③行动
调工具
④观察
看结果

关键点（原文强调）：每一步都要从环境拿到「ground truth」（真实反馈）——工具返回的结果、代码执行的输出，而不是模型"以为"的结果。Agent 靠这个判断自己进度对不对。

# 最小 Agent loop（伪代码，可直接映射成 PHP for 循环）
messages = [system_prompt, user_goal]
for i in range(MAX_ITER):          # 代码熔断保险丝
    resp = llm(messages, tools=tool_defs)   # ① 感知 + ② 推理
    if resp.has_final_answer:        # 模型自报完成
        break
    obs  = execute_tool(resp.tool_call)     # ③ 行动：调你的 API/DB/代码
    messages += [resp.tool_call, obs]       # ④ 观察：结果写回短期记忆
# 跑满 MAX_ITER 仍未完成 → 超时返回当前最优 + 告警

你后端写循环太熟了——区别只在：「下一步干啥、调哪个工具、传什么参」是模型每轮临时决定的，不是你写死的 `if/else`。这就是"自主"二字的全部含义。

2. 范式图谱：6 种可复用的模式

下面 5 种是 Workflow（流程由代码写死，可预测一致），最后 1 种是 Agent（模型自主控流程）。每个都标了「何时用 / 何时不用 / PHP 业务例子」。

Prompt chaining提示链

用：任务能干净拆成固定子步骤
不用：步骤间强依赖、需灵活分支
例：工单→先提取关键信息→再生成回复→再语气润色，三步串起来。

Routing路由

用：输入有明显不同类别，分开处理更好
不用：类别模糊、分类不准
例：用户消息先分类「咨询/投诉/退单」，各自进专门的提示与队列。

Parallelization并行化

用：子任务可并行，或多视角投票提置信
不用：步骤必须串行依赖
例：同时生成「技术文案+营销文案」再合并；或对同一答案跑 3 次取共识。

Orchestrator-workers编排-执行

用：事先猜不到要拆哪些子任务（如改哪些文件）
不用：子任务固定可知（那用并行化）
例：「给这个模块加缓存层」——先让模型规划要改哪些文件，再分派并行改。

Evaluator-optimizer评估-优化

用：有清晰评估标准、迭代能显著提质
不用：质量难量化、反馈无价值
例：先写 SQL，再让另一个模型按「是否命中索引/语义对不对」打分并返修。

Agent loop自主循环

用：步骤数无法预测、无法硬编码固定路径的开放问题
不用：简单任务——成本高风险大、错误会累积
例：「排查这次 500 错误的根因」——模型自己查日志、改配置、复跑，直到修好。

更全的对照见 架构范式速查。编排-执行 vs 并行化只差一点：子任务是否预先写死。

3. 选型判断法：拿到需求怎么选

Anthropic 首要原则：能简单解决就别上 Agent。按下面顺序从简到繁走，走到哪步够用就停：

单次能解决
加检索/示例优化一次 LLM 调用就够 → 不建 Agent
步骤固定
任务能拆成确定子步骤 → Prompt chaining
输入分类型
有明显不同类别分别处理 → Routing
子任务并行
可并行或多视角投票 → Parallelization
子任务未知
事先不知要拆哪些 → Orchestrator-workers
需迭代打磨
有评估标准、迭代能提质 → Evaluator-optimizer
开放难预测
步骤数无法预估、要灵活决策 → Agent loop
