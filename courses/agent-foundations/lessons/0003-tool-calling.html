课程 0003 · Tool Calling：模型与世界的接口

Agent Foundations · 概念层第 3 课 · 预计 9 分钟

前两课你懂了「Agent 是什么、循环怎么转、范式怎么选」。但循环里的「行动」到底是什么？——就是 Tool Calling（工具调用）。它是一份契约：你告诉模型有哪些工具、各自干嘛、参数长啥样；模型自己决定调不调、调哪个、传什么参；你执行后把结果喂回去。Anthropic 明确说：「工具集及其文档必须被设计得清晰、周到——这直接决定 Agent 成败。」

本课小胜（可验证）：学完你能写出一个工具定义的三要素（name / description / input_schema），并解释「为什么 description 写得好不好，比你的主提示词还关键」。

1. 它到底是什么：契约，不是魔法

用你后端工程师的语言类比最准：工具 = 一个带 JSON Schema 参数说明的 API 端点；模型 = 临时决定何时调用、传什么参的「调用方」；你 = 服务端。区别只在——「调不调、调哪个、传啥」是模型每轮现想的，不是你写死的路由。

2. 一个工具定义的三要素

name
动词化、无歧义的名字，如 get_order_status。模型靠它精确匹配。
description
这其实是给模型的「提示词」。要写清：这个工具干嘛用、什么情况下该用 / 不该用、参数怎么填。Anthropic 强调它应获得和你主提示同等的打磨投入。
input_schema
JSON Schema：参数名、类型、是否必填、枚举值、描述。越严，模型传的参越靠谱。
// 一个贴近你 PHP 业务的工具定义（伪 JSON）
{
  "name": "get_order_status",
  "description": "按订单号查询物流与支付状态。仅当已拿到明确 order_id 时调用；
                  若用户只给姓名，先不可用此工具，应改用 search_orders_by_user。",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string", "description": "形如 ORD-2026-0001" }
    },
    "required": ["order_id"]
  }
}

3. 一次完整的「往返」怎么接进循环

工具调用把第 2 课的循环接成了真实闭环。下面用 PHP 风格伪代码（你能直接映射成 Laravel 里一次 $client->messages->create()）：

// Agent loop 里接入 tool calling（PHP 伪代码）
$tools = [ /* 上面的工具定义数组 */ ];
$messages = [ ['role'=>'user', 'content'=>$goal] ];

for ($i = 0; $i < MAX_ITER; $i++) {
    $resp = $client->messages->create([
        'model' => MODEL, 'max_tokens' => 1024,
        'tools' => $tools, 'messages' => $messages
    ]);
    if ($resp->stop_reason !== 'tool_use') break; // 模型自报完成
    foreach ($resp->content as $block) {
        if ($block->type === 'tool_use') {
            $obs = call_user_func($block->name, $block->input); // 你的后端函数
            $messages[] = ['role'=>'user', 'content'=>[
                ['type'=>'tool_result', 'tool_use_id'=>$block->id, 'content'=>$obs]
            ]]; // 把真实结果写回「观察」
        }
    }
}

注意：你执行的不是模型的「想象」，而是真实后端函数（查库、调 API、跑代码）。返回的结果就是第 2 课说的 ground truth。

4. 为什么工具设计直接决定 Agent 成败

Anthropic 在附录「Prompt Engineering your Tools」给了关键经验（已核实）：

  • 工具定义值得和主提示同等的打磨。工具规格就是「提示」的一部分。
  • 提出 ACI（Agent-Computer Interface）类比：你为「人机界面（HCI）」投入多少精力，就该为「代理-计算机界面」投入同样多。把工具当产品界面来设计。
  • 格式选错，模型就写不对。例如「写 diff」要求先知道改动行数（难）；把代码塞进 JSON 比塞进 markdown 多了换行/引号的转义负担（易错）。选模型能可靠写出的格式。
  • 用 poka-yoke（防错设计）：让工具本身「不容易被用错」——参数加枚举、加校验、失败返回结构化错误而非裸文本。
  • 用大量样例测试模型实际怎么用你的工具，而不是凭直觉假设。

5. 新手最常踩的 5 个坑

✗ 描述太模糊　「获取信息」→ 模型不知道何时用、用错场景。✓ 写清用途 + 何时用 / 何时不用。
✗ 工具太多 / 重叠　20 个长得像的工具 → 模型选花眼、调错。✓ 少而精，职责清晰不交叉。
✗ Schema 太松　参数全 string、全 optional → 传来垃圾值。✓ 用枚举、类型、required 收紧。
✗ 错误只返回裸文本　「失败了」→ 模型无法恢复重试。✓ 返回结构化错误（错误码 + 原因 + 建议）。
✗ 不校验直接入库　模型参数当信任输入 → 注入 / 误写。✓ 服务端照常做鉴权、校验、白名单。
