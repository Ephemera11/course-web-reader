课程 0004 · 五种 Workflow 范式：可控编排的精华

Agent Foundations · 第 4 章 · 主推源：Anthropic《Building Effective Agents》

上一课我们搭好了「工具」这块地基——模型终于能调用外部能力。但光有工具还不够：怎么把多次 LLM 调用和工具调用组织成一条可靠的流程，才是工程的关键。

Anthropic 的核心主张是：绝大多数生产场景，用「工作流（Workflow）」就够了，根本不需要完全自主的 Agent。Workflow 是「预先定义好控制流」的 LLM 系统；Agent 是「模型自己决定控制流」的系统。本课把 Workflow 的五种范式逐一拆开，让你建立可落地的「选型直觉」——这正是 Mission 里「能判断一个需求该用简单 prompt / workflow / agent」那条成功标准。

给 PHP 工程师的锚点：五种 Workflow 其实对应你早就熟悉的后端控制流——
  • Prompt Chaining ≈ 管道（Pipeline）/ 责任链
  • Routing ≈ 网关路由 / 策略模式分发
  • Parallelization ≈ 并发请求 / 扇出（fan-out）
  • Orchestrator-Workers ≈ 主从任务分发（Master-Worker）
  • Evaluator-Optimizer ≈ 评审闭环（生成 → 校验 → 修订）
区别只在于：每一步的「worker」是 LLM + 工具，而不是普通函数。

1. Prompt Chaining（提示链 / 流水线）

把一个任务拆成一串有序步骤，上一步的输出作为下一步的输入。每一步可以有不同的提示词，甚至在不同模型间流转。本质上是「把复杂提示词拆小、分步验证」。

user │ ▼ [LLM #1: 提取要点] ──文本摘要──▶ [LLM #2: 据摘要写文案] ──文案──▶ [LLM #3: 润色/合规检查] ▼ final output
何时用任务能被清晰拆成固定子步骤，且上一步结果能稳定作为下一步输入（如：摘要→翻译→语气改写）
何时不用步骤间依赖动态、顺序会随输入变化——那该用 Orchestrator-Workers 或 Agent
真实例子「把会议录音转写→提取待办→生成 Jira 工单描述」；营销文案「大纲→正文→审校」

坑：别为了链式而链式。如果一步就能做对，拆开反而增加延迟与出错面。

2. Routing（路由）

先由一个「分类器」LLM 判断输入属于哪一类，再分发给专门处理该类的最小化 prompt / 模型 / 工具集。核心思想：不同问题用不同专家，别让一个通用提示词硬扛所有情况。

user query │ ▼ [LLM 分类器: 判断类型] ┌─────┼─────┐ ▼ ▼ ▼ [技术支持] [账单] [售前] 专用 prompt 专用 prompt 专用 prompt
何时用输入有明显类别差异，且每类需要截然不同的处理（语气、知识、工具）
何时不用问题高度同质、只是参数不同——直接一个 prompt 即可
真实例子客服系统按意图路由到退款/技术/投诉专员；代码助手按语言路由到对应 linter

3. Parallelization（并行化）

同一任务同时跑多个 LLM 调用，再汇总。两种形态：① 分片（sectioning）把一个大输入拆成几块并行处理；② 投票（voting）同一输入跑多次取多数/最优。利用的是「LLM 单次有随机性、并行可提质量与速度」。

user query │ ┌────────┼────────┐ ▼ ▼ ▼ [LLM A] [LLM B] [LLM C] ← 并行（分片 or 投票） └────────┼────────┘ ▼ [聚合: 合并 / 多数决]
何时用① 任务可无依赖拆分（长文档分段摘要）；② 需要「多次采样投票」提升稳健性（安全审查、答案校验）
何时不用步骤间有强依赖、必须串行——用 Chaining
真实例子「12 篇论文同时摘要再合并」；「同一道数学题跑 5 次取一致答案」做置信校验

4. Orchestrator-Workers（编排者-工作者）

一个「编排者」LLM 动态读输入，决定要派发哪些子任务、交给哪些 worker，再汇总结果。与 Routing 的区别在于：路由是固定分支，这里是运行时动态拆解，子任务数量和类型事先未知。

user query (复杂) │ ▼ [Orchestrator LLM: 拆解子任务] ┌────┼────┐ ▼ ▼ ▼ ← worker 数量/类型由编排者临时决定 [W1] [W2] [W3] └────┼────┘ ▼ [Orchestrator: 汇总成最终答案]
何时用任务复杂、无法预先规定拆解方式，需要模型临场决定怎么分活（如：改动涉及多个文件、需多方调研）
何时不用子任务结构固定——用 Routing 更简单可控
真实例子编程 Agent：读 issue → 决定改哪些文件 → 并行改 → 汇总 PR 描述

5. Evaluator-Optimizer（评估者-优化者）

一个 LLM 生成，另一个 LLM 当评审给出反馈，生成方据反馈迭代改进，直到评审通过或达上限。这是「人在环外」的自动质量闭环。

[Generator LLM] ──产出──▶ [Evaluator LLM] ▲ │ │ 反馈/打分/修改意见 │ 未达标 └────────────────────────┘ （循环直到通过）
何时用有明确可验证标准（编译通过、测试绿、篇幅达标），且一次生成难达标的场景
何时不用标准模糊、评审者也无法判断好坏——会陷入空转
真实例子「生成代码→跑单测→修到全绿」；「写文案→按品牌规范评分→重写」

选型决策小抄（回到 Mission 成功标准）

面对一个需求，按这个顺序问自己：
  1. 一个 prompt 能搞定吗？ 能 → 别上框架，直接写。
  2. 步骤固定且顺序已知？ → Prompt Chaining。
  3. 输入分几类、每类处理不同？ → Routing。
  4. 能并行、或要投票提稳健？ → Parallelization。
  5. 子任务结构运行时才知？ → Orchestrator-Workers。
  6. 有明确可验证标准、要反复打磨？ → Evaluator-Optimizer。
  7. 以上都不行，且需要模型自己决定接下来做什么？ → 才上 Autonomous Agent Loop（第 2 课）。

记住 Anthropic 的原则：能简单就别复杂。Workflow 可控、可测、便宜；Agent 灵活但难预测、贵、难 debug。

小测：检验你真的区分开了

选择题（每题独立，点选项看反馈）

Q1. 一个客服系统要先判断用户留言是「退款 / 技术故障 / 投诉」，再交给对应专员用各自的话术和工具处理。最适合的范式是？

Q2. 一个编程任务需要读 issue、临时决定改哪几个文件、并行修改后再汇总成 PR。子任务数量和类型事先无法确定。应优先用？

Q3. 下列哪种情况最不该一上来就用完全自主的 Agent Loop？

向你的 Agent 老师提问：如果某一题拿不准、或想知道「我的真实业务场景 X 该选哪种范式」，直接把问题丢给对话里的 Agent——它可以结合你的 PHP 后端背景给具体建议，也能补讲任意一种范式的代码骨架（概念清晰后再动手）。
