课程 0004 · 四道验收门：怎么证明它真的在记东西

TencentDB Agent Memory 入门 · 第 4 课 · 预计 18 分钟

这一课是整门课的核心。因为「装好了」和「在记东西」是两件完全不同的事，而这套系统在没记东西的时候也会返回成功。四道门是逐层收紧的过滤器，第四道门会告诉你真相。

本节目标：能用四条 curl 判断「记了没有 / 能不能搜回 / 抽没抽出记忆」，并知道哪个指标会让你误判。

门 1 · /health 返回 200，且三个字段合理

curl -s http://127.0.0.1:8420/health

实测返回（原样）：

{"status":"ok","version":"0.1.0","uptime":0,
 "stores":{"vectorStore":true,"embeddingService":false},
 "services":{"timerScanner":{...},
             "pipelineWorker":{"tasksConsumed":0,"tasksCompleted":0,"tasksFailed":0,...},
             "stateBackend":"connected"}}

要看的不是 status:ok，而是这三个

stores.vectorStore存储层可用（true 才对）
stores.embeddingServicefalse = 没配 embedding，只能关键词检索。这不是故障
services.stateBackendconnected = 调度器真的在跑，不是空壳

门 2 · 写一轮对话，L0 真的落库

curl -s -X POST http://127.0.0.1:8420/capture \
  -H "Content-Type: application/json" \
  -d '{"user_content":"我在维护招投标情报系统，后端 FastAPI。",
       "assistant_content":"已记录：后端 FastAPI。",
       "session_key":"tutorial-01"}'
{"l0_recorded":2,"scheduler_notified":true}

l0_recorded:2 是一条用户消息 + 一条助手消息。scheduler_notified:true 表示调度器收到了通知。连发 5 轮，每轮都是这个结果。

门 3 · L0 能搜回来（唯一不会骗人的门）

curl -s -X POST http://127.0.0.1:8420/search/conversations \
  -H "Content-Type: application/json" \
  -d '{"query":"招投标","limit":3}'
Found 2 matching message(s):
---
**[user]** Session: tutorial-01 [...] (score: 0.686)
我在维护 wty-information 招投标情报系统，后端 FastAPI + SQLite，前端 Vue3。
为什么这门最硬：它不需要你相信任何计数器、不依赖 LLM、不依赖配置对不对——内容从库里搜出来了，就是记下了。只要这道门不过，后面所有门都不用看。

门 4 · L1 记忆能不能搜到（会安静地失败）

curl -s -X POST http://127.0.0.1:8420/search/memories \
  -H "Content-Type: application/json" -d '{"query":"技术栈","limit":3}'
# → {"results":"No matching memories found.","total":0,"strategy":"fts"}

curl -s -X POST http://127.0.0.1:8420/recall \
  -H "Content-Type: application/json" \
  -d '{"query":"我这套系统用什么技术栈","session_key":"tutorial-01"}'
# → {"context":"","memory_count":0,"code":0,"message":"ok","retryable":false}
这里最容易误判：HTTP 200、code:0、message:"ok"——一切看起来正常，但 context 是空的。「返回 ok」不等于「召回到了东西」。空字符串就是空，它用一种成功的方式表达了失败。

哪一个是会让你误判的指标

官方文档说「期望看到 tasksConsumed / tasksCompleted 随对话增长」。我实测：5 轮对话后 tasksConsumed=5, tasksCompleted=5, tasksFailed=0 —— 全绿。而库里 l1_records 是 0 行。

# 停掉 gateway 之后直接读库
>>> sqlite3.connect("C:/tdai/memory-data/vectors.db").execute(
...     "select count(*) from l0_conversations").fetchone()
(10,)   # 5 轮 × 2 条，L0 全在
>>> ...execute("select count(*) from l1_records").fetchone()
(0,)    # L1 一条都没有

原因写在源码里（src/core/record/l1-extractor.ts:178-181）：LLM 提取抛错时，它返回 {success:false, extractedCount:0}，而任务本身仍被标记为完成。所以「任务完成」只证明调度器跑过，不证明抽出了东西。

替换判据（记这三条，任一条成立才算 L1 通了）：
① /search/memories 返回 total > 0
② /recall 返回非空 context
③ 停进程后读库 l1_records 行数 > 0

两个读数据的陷阱

做法结果正确姿势
gateway 活着时用 sqlite3 读 vectors.db读到 0 行（WAL 未 checkpoint），误判「没落库」停进程后读，或只信 API
只看 conversations/ records/ 目录有没有文件目录会创建但可能为空，数据在 SQLite 里别用文件数量当验收依据

持久化验证：重启后还在吗

停掉进程 → 用同一个 TDAI_DATA_DIR 重新起 → 再搜同样的关键词。

实测：重启后 tasksConsumed 归 0（计数器重置），但搜索结果仍然是 total=2、score 仍然是 0.709 / 0.686。数据真的在库里的，不是内存态。
