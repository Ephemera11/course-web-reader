课程 0009 · Proxy 的八个阶段：记忆是怎么被塞进 prompt 的

TencentDB Agent Memory 入门 · 第 9 课 · 预计 15 分钟

这一课讲这套设计里最巧的一层：它靠"假装成 LLM 的 API"来给 agent 加记忆。不改客户端一行代码、不改协议，只在转发的一进一出之间动手。理解这八个阶段，你就知道为什么有些客户端"什么都不用配"、而 Hermes 必须手填四个 header。

本节目标：能说清一次请求经过哪些阶段、哪些层是"注入"哪些层是"工具查询"，以及无表单客户端为什么会静默失效。

1. 透明代理是什么意思

proxy 原样转发 OpenAI /v1/chat/completions 和 Anthropic /v1/messages，协议一个字节都不改。对客户端和上游来说它是透明的——变化只发生在中途。

这就是"零代码接入"的真相：把 agent 的 base URL 指到 proxy 就完事，不需要插件、hook 或 MCP server。代价是——所有能力都只能通过"改 prompt / 改返回"来实现，不能要求客户端配合。

2. 八个阶段

1 auth — 校验 x-tdai-user-key，解析出 user_id 当全链路身份
2 systemUser — 命中内部服务账号就短路，只做透明转发 + 计费
3 sessionInit — 首次对话弹表单：team → agent → task；或从请求头预选
4 injection — 把 skill / knowledge / memory 注入 system prompt
5 rateLimit — 按 spaceId × 最终模型 做 60 秒滑动窗口限流
6 forward — 转发到上游 LLM
7 extract — 一轮结束后异步回流：对话切片发给 core，同时写 L0
8 report — ClickHouse / Langfuse / Opik / 计费上报，任一路失败不影响业务
看第 3 和第 7 的位置：初始化在转发之前，回流在转发之后。所以 memory 的写入天然是"异步、不阻塞回答"的——这也解释了为什么你在对话里感觉不到延迟，但也意味着"刚说完立刻去搜"可能还搜不到。

3. 四层记忆，两种接法

这是整个设计里最值得学的一个决策：不是所有记忆都塞进 prompt。

层是什么怎么进模型
L0短期对话记忆每轮由 proxy 主动写回 core（不注入）
L1会话级关键记忆通过 <tdai_memory_tools> 让模型自己按需召回
L2Agent Profile直接注入 system prompt
L3Team / Global 记忆直接注入 system prompt
为什么这样分：L2/L3 是"总是需要"的背景知识，量小、稳定，直接注入。L0/L1 量可能很大且每题不同——如果每轮都塞进去，上游的 KV cache 前缀就变了，缓存全失效，成本和延迟都会飙。所以改成"给工具让模型自己查"。

这是 prompt 工程里一个很实用的原则：按"是否每次都需要"分层，而不是按"重不重要"分层。

4. 四个注入块长什么样

块内容
<cloud_skills>从 RAG 检索到的相关 Skill 摘要
<skill_tools>教模型怎么 curl 调用 Skill（写权限由 skillRuntime.allowLlmWrite 控）
<knowledge_tools>Wiki / CodeGraph 的两步自发现工具
<session_context>session init 后每轮追加的 agent / task 信息

这些都是 XML 结构的文本块，塞进 messages[0].content（system message）。所以模型"看到"的其实是普通文本，不是某种特殊协议——这也是为什么用错客户端格式时它们会失效。

5. 表单 vs Header 预选：Hermes 为什么必须手填四个 header

客户端类型sessionInit 方式缺信息时
有 UI 工具能力的（Claude Code / CodeBuddy / Codex…）proxy 返回一个「表单工具调用」，客户端弹选项弹表单让用户选
Hermes / OpenClaw只能靠 header 预选静默 bypass：不注入、不报错

Hermes 无法响应 proxy 返回的 function_call，所以只能这四条全带：

x-team-id:         <team_id>
x-agent-id:        <agent_id>
x-task-id:         <task_id>          # 当前版本必填
x-conversation-id: <你自己生成>      # 每个新会话要换
这就是"配了却不生效"的机制层原因：缺任意一个 header，proxy 会退回表单路径；Hermes 响应不了表单，于是 bypass。整个过程 HTTP 200、对话正常，只是记忆注入那部分被跳过了。没有报错，是最难查的那类故障。

两个补丁手段：

sessionInit.defaultTaskId: "no-task"不想绑 Task 时，让 proxy 在任务列表最前面插一条虚拟条目兜底（这个 ID 不需要真实存在）
headerAutoSelect.onMismatchheader 与真实数据不匹配时的行为（form 或跳过）

6. 排查代理问题时用这两个开关

PROXY_DEBUG_DUMP_INBOUND=1   # 打印进站 body
PROXY_DEBUG_DUMP_BODY=1      # 打印出站 body

对比进出两个 body，就能看出注入块到底有没有被塞进去、客户端的特色字段（比如 reasoning_content）有没有在序列化时被抹掉。这是排查「注入似乎没生效」最直接的手段——比猜配置快得多。
