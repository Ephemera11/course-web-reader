课程 0005 · 保留消息与遗嘱消息

MQTT 深入 · 第 5 课 · 预计 14 分钟

MQTT 有两个「反直觉但极有用」的机制：保留消息让新订阅者立刻拿到最新状态；遗嘱消息让设备突然断线时 Broker 替它广播「我掉线了」。这课讲透它们解决什么问题、怎么配。

本节目标：能解释保留消息解决「晚到订阅者拿不到状态」的问题，能解释遗嘱消息解决「异常断线无人知晓」的问题。

1. 痛点：晚到订阅者什么也收不到

MQTT 默认只转发「订阅之后」的消息。一个 App 中午 12:00 订阅 device/status，那 11:59 设备发的「在线」它永远不知道——直到下一次状态变化。对「状态类」信息，这很致命。

2. 保留消息（Retained Message）

发布消息时置 retain 标志，Broker 会为这个 Topic 记住最后一条。新订阅者订阅时，Broker 立刻把这条保留消息发给它：

// 伪代码：发布时置 retain=true
publish('device/status', 'online', { retain: true });
典型用途：设备状态（在线/离线）、窗帘位置、灯亮度、固件版本——「当前值是什么」这类状态，而不是「每秒发生什么」的事件。事件用普通消息，状态用保留消息。

3. 遗嘱消息（Last Will）

客户端连接时先声明遗嘱：指定一个 Topic 和一段内容。如果客户端异常断线（网络断开、断电、崩溃——而不是正常 DISCONNECT），Broker 自动替它发布这条遗嘱：

// 连接时声明遗嘱
connect({
  will: {
    topic: 'device/status',
    payload: 'offline',
  }
});

效果：设备崩溃后 1-2 秒内，所有订阅 device/status 的人都收到「offline」——不用轮询、不用超时判断。

4. 两者结合：状态机经典组合

正常启动发 retain 消息「online」新订阅者立即看到在线
正常退出发 retain 消息「offline」再断开状态更新为离线
异常掉线Broker 发遗嘱「offline」无需设备配合，自动广播离线
